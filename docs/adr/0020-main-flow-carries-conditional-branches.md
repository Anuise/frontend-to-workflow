# Main flow diagram 帶業務條件分歧，每個出口以 evidence 逐字引用畫面上的操作當事實憑據

Main flow（主線）上的一步由「只能往下一步推進」改成**可以有任意條出口**。契約上 `steps[].edgeLabel`（單一字串）**退場**，改成每一步一個 `steps[].outcomes[]`，每個出口是 `{ condition, target, evidence }`：`condition` 是 ≤8 字的條件措辭（沿用 `EDGE_LABEL_MAX`）、`target` 是**同一條主線**裡的步號（1 起算，可指回前面＝迴圈，不得指向自己）、`evidence` 是 `{ route, tab?, label }` ——**逐字**指向 `workflow.json` 裡某頁的某個 `actions[].label`。終點步要**明寫** `"outcomes": []`，單出口就是長度 1 的 `outcomes`。一步有 **≥2** 個出口，圖上就在該步右邊長出一個**菱形決策點**。同時 `STEPS_MAX` 由 10 放寬到 **20**，主線推論的素材由「`overview` ＋ 逐頁 `purpose`」擴成「逐頁 `purpose` ＋ `content` ＋ `actions[].label` ＋ **該頁截圖**」。

本 ADR 取代 **ADR-0008 的「邊 label 的來源」一節**（`edgeLabel` ＋ 相鄰步的 `edgeLabel` 位置規則）與**「相鄰兩步在 `workflow.json` 裡接不上時」一節**（`requireRealEdges` 的 destination 硬驗），以及 **ADR-0009 的「步數區間」一節**的上限數字（10 → 20，下限 1 不動）。兩份 ADR 其餘各節——主線邊界＝頂層 Page 分類、分頁名照抄、推論落在可手改的 `mainflow.json`、只留主幹、一步可收多頁、涵蓋完整性硬驗、圖上不標「推論·待確認」與 ⚠、確定性範圍——以及 **ADR-0010 的總覽頁**（最後一頁、原樣堆疊）**全部續用**。**ADR-0006 的三項**（明文不壓縮、邊座標交給 draw.io、圖上收掉的資訊降 tooltip）也照舊。

起因是把 ADR-0009／0010 的圖交出去之後拿到的回饋：「沒把細部操作的流程或條件判斷寫出來」。這句話裡是兩件事，本 ADR 只做後者。**細部操作不展開**——wizard 的每一步、詳情頁的每個 tab 仍然收攏進一步、只進 tooltip，理由與 ADR-0008「只留主幹」相同：業主不需要知道按編輯會開彈窗。但**條件判斷是真的缺**：0729 專案的「人機協作」主線裡，人工覆核之後是**通過**還是**未通過**、未通過要**退回哪一步**，是這條主線最有業務含量的一格，而 ADR-0008 的契約根本表達不了——一步只能有一個 `edgeLabel`、只能指向 `index + 1`。順帶一提，ADR-0005 當年把「業務流程圖（含決策條件）」列為否決選項，理由是「`workflow.json` 沒有這些資訊，只能由 AI 推論，等於再開一個推論維度」；ADR-0008 已經把那個維度打開了，所以這條反對意見在今天已經不咬人。

## Considered Options

**推論素材的來源**

- **(i) 只把逐頁 `content` 與 `actions[].label` 納入推論素材**：兩者本來就在 `workflow.json` 裡，讀進來零成本、零新依賴，而且 `actions[].label` 就是後面 `evidence` 要逐字引用的那個欄位——不讀它根本填不出 `evidence`。但只有這些時，AI 判斷「這兩個按鈕是同一個決策的兩個分支，還是兩件不相干的事」全靠措辭猜：`核准`／`駁回` 猜得出來，`儲存`／`送審`／`匯出` 三顆並排就猜不準了。
- **(ii) 再加讀該頁截圖**：版面把措辭猜不到的東西直接說出來——並排在同一列的兩顆按鈕、右下角的一組主要／次要按鈕、彈窗底部的確認列，都是「這是一個決策點」的視覺證據。代價：推論步要多讀 N 張圖，token 成本與延遲隨頁數線性增加，而且截圖**不可斷言**——同一份輸入換一次模型可能推出不同分步。
- **(i + ii)（採用）**：兩者都讀。並且劃一條界線：**截圖只進推論、不進驗證、不進頁集合**。`workflow.json` 仍是頁集合與涵蓋完整性硬驗（`requireExactCoverage`）的唯一權威，`evidence` 驗的也是 `workflow.json` 的 `actions[]`、不是截圖上的像素。所以截圖貴、但貴在推論那一次；出錯時 `mainflow.json` 仍然可手改、硬驗仍然擋得住。
- **(iii) 完全改讀截圖、取代 `workflow.json`（否決）**：看起來最直接——反正真相就在畫面上。但這會**砍掉涵蓋完整性硬驗的權威來源**：頁集合一旦來自「AI 這次看了幾張圖」，「圖上少了哪一頁」就永遠查不到，`excludedPages` 那條「每一頁都要表態」的規則同時失效。ADR-0008 為了補上零推論的消失特地立了這條硬驗，不能反手拆掉。

**分歧邊的事實墊背**

- **(α) 放寬不驗**：`condition` 反正是 AI 寫的字，那就別驗了，圖畫得出來最重要。但這等於把 ADR-0008 唯一撐住「圖有事實基礎」的機制拿掉，圖從「業務措辭 ＋ 結構可回溯」退化成「一份好看的猜測」，而收圖的是業主。
- **(β) 維持 `requireRealEdges` 的 destination 硬驗（否決）**：這是 ADR-0008 的原設計——相鄰兩步之間要有一條真實的 `destination` 邊墊背。實跑立刻打臉：純前端 demo 的**寫入動作**（核准、駁回、送出、刪除）一律只記錄不執行，`destination` 全是 `null`。也就是說**最該畫成分歧的那些操作，恰好一條去向都沒有**——維持這條硬驗，等於用驗證把本 ADR 想解決的問題永久擋在門外。
- **(γ) 擴充事實的種類，但要求逐字引用（採用）**：把「事實」由「這條 `destination` 存在」擴成「**這個畫面上有一顆叫這個名字的操作**」——後者同樣是 f2w-capture／f2w-describe 觀察得到、可回溯的事實，只是不含去向。`requireEvidencedOutcomes` 驗三件事：(1) `evidence` 那一頁必須屬於**來源步自己的 `pages`**（不能拿別步的畫面替這一步作證）；(2) `evidence.label` 必須**逐字**命中 `workflow.json` 那一頁的 `actions[].label`；(3) 該 action 若 `destination` **非 null**，那個去向必須落在 **`target` 步的 `pages`** 裡。第 3 條讓舊的 destination 硬驗在「真的有去向」時原封不動地繼續成立，只是不再是唯一的過關方式。代價：`evidence` 是三個欄位的手抄，AI 抄錯一個字就整份 build 失敗——但這正是要的，錯字比錯圖便宜。

**契約形狀**

- **(X) 巢狀 `branches`**（一步底下掛 `branches[]`，每個分支再掛一串 steps）：讀起來像樹、直覺；但**表達不了往回的迴圈**。「未通過 → 退回第 2 步重新送件」在樹裡沒有寫法，只能複製一份第 2 步當葉子——步號從此對不上、tooltip 裡同一頁出現兩次，`requireExactCoverage` 的「每頁只出現一次」當場破功。而退件迴圈正是業務條件分歧最常見的形狀。
- **(Y) 顯式 `nodes` ＋ `edges`**（人自己配 id，邊寫 `from`／`to`）：表達力最強，任何圖都畫得出來。但 `mainflow.json` 是**可手改的逃生口**——ADR-0008 立它就是為了「AI 推錯，人改檔重跑，不用改程式」。改成 id 圖之後，手改一步得同時維護節點 id、所有指向它的邊、以及圖上的顯示順序，**id 維護成本落在逃生口上**，逃生口就沒人願意用了。
- **(Z) 線性 `steps` ＋ `outcomes` 指步號（採用）**：步驟仍是一個有序陣列（手改時的心智模型不變、步號就是圖上的編號、業主能用「第 3 步」指稱），分歧只是「這一步的出口不只一個」。迴圈是 `target` 指回前面的步號，天然可寫。代價：**`target` 限同一條主線**（見 Consequences 的限制一節），而且插一步要重編後面的 `target` ——手改一步的代價從 O(1) 變成 O(步數)。接受，因為主線最多 20 步。契約層另加兩道 refine 擋掉線性表示法特有的壞形狀：`hasValidOutcomeTargets`（`OUTCOME_TARGET_RULE_MESSAGE`：步號要合法、不得指向自己）與 `hasNoOrphanSteps`（`ORPHAN_STEP_MESSAGE`：除第 1 步外每一步都要被某個 `target` 指到，否則圖上是接不到的孤兒框）。

**多出口在圖上怎麼畫**

- **從步驟框直接拉多條帶 label 的邊**：圖元最少、不必算新座標。但這是 ADR-0005「多出口」那一節否決過的隱式分歧，理由今天更成立：三條邊從同一個方框右緣散開，看圖的人分不出「這是三個並列的後續動作」還是「這是一個三選一的決策」——而後者正是這張圖新增的全部價值。
- **插一個菱形決策點（採用）**：**沿用 ADR-0005 對 gateway 的論證**（分歧走專屬圖元、語意明確、日後掛條件有現成掛點），只是這次畫在 draw.io 而不是 BPMN，所以是純視覺的菱形、不是 `exclusiveGateway` 元素。實作上是 `DiagramNodeKind` 加第四種 `"decision"`：60×60、與該步同色系、**不寫字**（條件字都在出去的邊上，菱形裡再寫一次是重複），夾在該步右緣與下一步左緣之間（`240 + 20 + 60 + 20 = 340`＝`COLUMN_SPACING`）、垂直置中對齊步驟框。`step → decision` 一條**無 label** 的邊，`decision → 各 target` 各一條帶 `condition` 的邊。關鍵約束：菱形**不佔步號、不寫進 `mainflow.json`**——它是 layout 從 `outcomes.length >= 2` 推出來的，契約裡沒有這個概念。代價：分歧步的圖元數多一倍，而且橫向要多讓一段（見下）。

## Consequences

- **取代 ADR-0008 的「不含業務決策條件」與 ADR-0009 的步數上限**：ADR-0008 的圖只畫得出一條沒有分岔的鏈，那條限制到此為止。步數上限 10 → 20（`STEPS_MAX`）是分歧的直接後果——分歧把「一個決策的兩個結果」變成兩條可見的路徑，同樣一個模組要切得比以前細才畫得出決策點；0729 的 `算力排程與工作負載`（15 頁）在 10 步上限下已經沒有餘裕再拆。下限維持 1（ADR-0009 的理由沒變：只有一頁的分類就是一步）。
- **`edgeLabel` 退場，單一表達方式**：不保留 `edgeLabel` 當「單出口的簡寫」——同一件事有兩種寫法，就會出現「兩個都填、且互相矛盾」的檔，驗證得多一條規則去擋，讀者得多記一條規則去讀。單出口就寫長度 1 的 `outcomes`，多一點字，換 single source of truth。連帶：ADR-0008「`edgeLabel` 掛在來源步、最後一步不得有」那條位置規則整條消失，改由「**每一步都要表態**」承接——終點步明寫 `"outcomes": []`，於是「漏寫」與「刻意走到底」在檔案上分得出來（與 `excludedPages` 同一種設計）。
- **單列橫排保留，但主線高度不再一致**：頁內仍是單列橫排、不折行（ADR-0008），只是步驟 x 座標由「序號 × `COLUMN_SPACING`」改成**逐步累加**，分歧步多讓 `BRANCH_EXTRA = 160` ——不多讓的話，菱形出去的 `condition` label 會疊在下一步的框上。跳步與迴圈邊帶 `waypoints`，一條佔一條主線下方的**繞路帶**（`DETOUR_GAP` 60 起算、每條 `DETOUR_LANE` 60）；不給 waypoints 的話 draw.io 走最短路徑，會直接橫穿中間那幾個步驟框。這兩件事合起來讓一條主線的高度變成**算出來的**（`laneHeight`＝標題與步驟高度 ＋ 繞路帶），所以 **ADR-0010 的總覽頁堆疊由固定 `ROW_SPACING`（310px）改成累計 `laneHeight` ＋ `LANE_GAP`（80px）**。ADR-0010 的其餘決定（最後一頁、同一段 layout 程式產兩種頁、`Overview_` id 前綴）不動；固定間距在主線帶了分歧之後會讓長主線壓到下一條。
- **跨主線的分歧畫不出來，這是刻意不支援**：`outcomes[].target` 限**同一條主線**的步號。實例：new_0724 的登入頁有兩條出口（SSO 登入 → `叢集資源總覽`、一般登入 → `算力申請與審核`），這兩個去向跨了兩條主線，於是圖上的登入會是一條 1 步、`outcomes: []` 的主線，**那個分歧在圖上消失**。不支援的理由是分頁邊界：ADR-0009 定了「一條主線一張分頁」，跨主線的邊要畫在來源那一頁還是目標那一頁，沒有好答案——畫在來源頁就得把目標主線的步驟也搬過來（分頁不再是一條主線）、畫在總覽頁就變成只有總覽有的資訊（分頁與總覽不再逐字相同，破 ADR-0010）。這與 ADR-0009 已經接受的代價是同一條：跨模組的業務串接不畫在任何一頁，只留在 `workflow.json` 的去向與 `workflow-<時戳>.xlsx`。要解得先重開「主線邊界」那個決策，不是加個欄位。
- **不折行，最壞情況很寬**：20 步 × `COLUMN_SPACING` 340px ≈ **6760px**（分歧步還要各加 160px），列印時會縮到看不清字。**先不處理**——0729 實跑最長的主線只有 7 步，`STEPS_MAX` 20 是上限不是常見值。等到真的有專案量到十幾步再談折行或分頁切割；提早設計折行會讓 layout 多一個維度，而折行本身會破壞「用 x 座標讀順序」這個目前免費拿到的性質。
- **四道硬驗的名單換了一項，數目不變**：`requireKnownDestinations`／`requireSameProject`／`requireExactCoverage` 不動，`requireRealEdges` 換成 `requireEvidencedOutcomes`。錯誤訊息一律點名「主線『X』第 N 步『title』的出口『condition』」，收尾指向修法（改 `target`、重新分步、或把憑據換成本步的頁）——沿用 ADR-0008「接不上就改 `mainflow.json`，不畫虛線、不放寬驗證」的處置。
- **圖上仍然不標「推論·待確認」、不標 ⚠**：ADR-0008 第 4 點照舊，讀者是業主。分歧是這張圖上推論成分最重的部分（`condition` 的措辭、哪兩個出口算同一個決策，都是 AI 判斷的），但表態的地方是 `mainflow.json` 的 `evidence` ——每個出口都指得出「我是根據畫面上這顆按鈕畫的」，人要覆核就比對那三個欄位。這比在圖上打一個看不出意思的驚嘆號有用。
- **確定性範圍再縮一格**：`buildDiagram` 仍是純函式、同一份 `workflow.json` ＋ `mainflow.json` 兩次序列化仍逐字元相同、座標仍可斷言。但推論素材加了截圖之後，**從 `workflow.json` 到 `mainflow.json` 這一段的可重現性又低了一截**——同一份輸入換一次模型可能推出不同的分步與分歧。這一段本來就不確定（ADR-0008 起就是），差別在於現在連「AI 讀了什麼」都不再完全落在版控裡（截圖在 `output/<project>/screenshots/`）。`mainflow.json` 已存在就沿用、不重推論這條規則因此更重要，不是可有可無的優化。
- **匯出仍要真的看一眼**：ADR-0008／0009／0010 一路的教訓照舊，而分歧讓它更硬——`BRANCH_EXTRA` 與繞路帶這兩個常數都是**匯出來看到 label 疊框、邊橫穿方框**之後才加的，單元測試全綠的版本裡它們並不存在。改過 layout 就匯出，不要只讀測試綠燈。
