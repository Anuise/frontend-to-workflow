# 派工輸入由 workspace/spec/<project>/ 的目錄慣例自動發現，目錄名即分工方名

`f2w-breakdown` 自己去 `workspace/spec/<project>/` 找派工輸入，不再要求使用者每次觸發都打路徑：project 根的 `.drawio` 是權責泳道圖，`<方名>/*.json` 裡過 OpenAPI 指紋的是那個方的 Vendor spec。**目錄名即分工方名**——`gary/Gateway-API.json` 屬於 `gary`，不必另立對應表。使用者仍可手動指定路徑覆蓋發現結果。

現行做法是供應商識別名＝**檔名**去副檔名，於是「哪份 spec 屬於哪個方」這個事實只活在一支未納版控的驅動常數裡（`SPEC_OWNER: { aidms: "leadtek", … }`），而 `partySet = 泳道名 ∪ spec 檔名` 讓沒被任何工項引用的 `IDP-service.json` 憑空成為一個合法的 `assignedParty`。改成目錄名之後，映射是確定性推導、零新增契約，而分工方集合純由泳道名決定（ADR-0014），spec 目錄名必須是泳道名的**子集**，不是即報錯——多一道新防線。

`workspace/spec/<project>/aidms/` 因此改名為 `leadtek/`。`aidms` 是產品名，而這一層要回答的是「誰負責」。

## Considered Options

- **維持觸發時強制指定路徑（否決）**：`new_0724` 要打一張圖＋四份 spec 共五個路徑，每次重跑都打一次，而那五個路徑本來就在固定位置。這也是 `SPEC_OWNER` 這種未落檔事實得以存在的原因——路徑既然是手打的，方名也就順手寫在驅動裡。
- **保留產品名目錄，另立一份 spec→方 的宣告檔（否決）**：得為它決定落在哪裡，而 ADR-0011 已明文否決把逐 project 的東西放進特定位置，還得先為它找位置；自動發現也從「掃目錄」變成「掃目錄＋讀一份新契約」。多一個真相來源換一個產品名。
- **要求每份 OpenAPI 檔內以約定欄位自報所屬方（否決）**：動到供應商給的檔本身，下次供應商換一版就要重新加回去。
- **目錄名即分工方名，掃描＋可手動覆蓋（採用）**：唯一不新增契約就能把「spec 屬於誰」落檔的做法，順帶消滅 spec 檔名成為合法方名這個舊行為。

## 找不到輸入時分兩種嚴格度

合併掉 `f2w-sourcing` 之後，「這一步不觸發就是明確沒派工」這層防線必然消失（ADR-0015），取而代之的是一個推斷。推斷分兩種：

- **`workspace/spec/<project>/` 目錄不存在**＝安靜照跑、不產 `partyChain`。純自建專案（如 `0714`）什麼都不用做。
- **目錄存在但沒有任何可用檔**＝**中止**。那更像擺錯位置或忘了放，而不是「這個專案不派工」。
- **手動指定**＝用指定的、忽略發現結果。

發現結果**每次都列給使用者看**：用了哪張圖、哪幾份 spec、各自推出哪個方、哪些檔被排除，或明說一份都沒找到所以本次不派工。這是「有泳道圖但擺錯位置」這種靜默失敗的唯一防線。

## Consequences

- `.$*` 與 `*.bkp` 依**檔名**排除。draw.io 的自動備份本身是合法 mxfile，`diagram` 的 name 與 id 與正本相同，內容指紋分不出來。（實檔的 `.$桃園刑大ai_platform.drawio.bkp` 落在 `workspace/spec/` 根、不在 project 目錄內，天然不會被掃到，但備份也可能出現在 project 目錄裡。）
- OpenAPI 指紋以根物件的 `openapi`／`swagger` 欄位判定；不過指紋的 `.json` 一律列進「已排除」並說明原因，不靜默略過。
- 同一方目錄下多份 spec 全部解析並合併成該方的 capability 集合；不同目錄同檔名不再衝突，因為識別名來自目錄。
- ADR-0011 其中一條否決理由裡「泳道圖是平台級共用文件、可跨 project」的說法與現實不符（實際住在 `workspace/spec/<project>/`），本 ADR 一併改為逐 project；ADR-0011 的結論不變。
- ADR-0007「Vendor spec 是人提供的輸入、放 Workspace」不變，只是把「觸發時強制指定路徑」放寬成「自動發現＋可手動覆蓋」。
