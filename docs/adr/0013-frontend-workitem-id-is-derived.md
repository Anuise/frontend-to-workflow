# 前端工項 id 為確定性推導，後端不是

前端 Work item 的 id 由契約強制成 **`FE-<頁序>-<該頁工項序>`**（兩段皆從 1 起、補零兩位），兩個序號都取自 `workflow.json` 的陣列索引。`buildWorkitems` 逐筆比對 AI 給的 id 是否等於 `frontendWorkitemId(pageIndex, itemIndex)` 的推導值，不等就丟 `WorkitemsConsistencyError` 指名該筆。

原本的契約只要求 id 非空且全域唯一。實測資料裡的 `FE-01-01` 是 AI 的習慣，不是強制。重跑 `f2w-breakdown` 時 AI 重新拆、重新編號，id 一漂，所有錨在 id 上的修訂全變孤兒——workitems 那一半的修訂功能會形同虛設。這是 ADR-0012 的前提條件，不是獨立的整理。

## Considered Options

- **維持「非空且唯一」，靠 AI 自律（否決）**：實測 41 頁專案的驅動確實穩定產出 `FE-01-01` 格式，但那是驅動寫死的，不是契約保證的。沒有把關的慣例撐不過一次改寫。
- **只加格式 refine，不比對推導值（否決）**：`FE-07-03` 合格式卻可能編在第 2 頁上，格式對、語意錯，而修訂錨的是語意。
- **由 `buildWorkitems` 直接改寫 id、不理 AI 給的值（否決）**：AI 若把工項的頁歸屬或順序搞錯，id 會被**靜默**重新指派，而 `dependsOn` 與後端工項對前端 id 的參照就指到語意錯誤的對象；要嘛還得把整組 `dependsOn` 一起重映射，把一個檢查換成一次資料改寫。
- **格式 refine ＋ 逐筆比對推導值（採用）**：AI 編錯就大聲丟錯，`dependsOn` 不必重映射，公式匯出成 `frontendWorkitemId` 給驅動與測試共用，只有一份。

## 後端 id 做不到，這是明確接受的取捨

`BE-<...>` 的序號取決於 AI 這次推論出幾筆，每次可能不同。把後端也錨定到 action 以求確定性會限縮 ADR-0002 給推論的自由度（後端工項刻意不與 action 一一對應），**不做**。後果分兩種：

- **`upsert` 補 AI 漏掉的後端工項** — 使用者可用自訂 id（如 `BE-EXTRA-01`），完全穩定。這是後端修訂的主要用途。
- **`set` 改 AI 寫錯的後端工項** — 錨在 AI 生成的 id 上，重跑後可能孤兒。這一種脆。

## 殘餘風險：id 位移不會變成孤兒，會落到別人身上

前端 id 確定性化解決了「重拆後 id 亂跳」，但沒有解決 `workflow.json` 真的變了的情況，而且實際行為比「變孤兒」更難察覺：

**新頁插在中間時，既有頁的頁序往後推，原本錨在 `FE-02-01` 的修訂不會落空——它會套到位移後占用 `FE-02-01` 的那筆工項（插進來那頁的工項）身上，而且不發 warning**，因為那個 id 確實存在。原本被校正的那頁退到 `FE-03-01`、拿回 AI 的新文字。

根因是 anchor 只有一個 id，沒有頁身分可以交叉核對。乾跑也看不出來（沒有孤兒可報）。目前接受這個風險：新頁插在中間需要 `pages.json` 的既有頁序改變（f2w-capture 通常是往後追加），而修訂的 `reason` 欄位留了人工回查的線索。要根治得在 anchor 上補 `sourcePage` 或改用內容雜湊，那是另一張票。這條行為有測試直接蓋到（`src/revise/crossRerunSurvival.test.ts`），避免將來被當成 bug 誤修。

`workflow` 那一半沒有這個問題：錨是 Page 識別（route ＋ tab），來自 `pages.json`，本來就確定性，插頁不影響既有頁的錨。

## Consequences

- 契約多一條 refine，訊息指名不合格式的那筆 id。後端工項不受此格式約束，且有測試直接蓋到（避免未來有人順手加上去）。
- 「該頁工項序」是**該頁第幾筆工項**，與 action 索引在 1:1 時相同；顆粒度底線只規定下限，某頁多拆幾筆時序號繼續往下編（`FE-01-03` 可以存在於只有兩個 action 的頁上）。
- 既有的 0714 專案驅動原本用 `FE-P01-A1` 格式，已改為呼叫 `frontendWorkitemId` 並重跑落檔。
- 41 頁／257 action 的 `new_0724_AI六大模組管理平台_桃園智發會_最新版` 連跑兩次 `f2w-breakdown`，前端 id 集合逐字相同（257 筆，SHA-1 `c7370a0c`）。
