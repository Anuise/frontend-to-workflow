## What to build

證明這個 feature 真的兌現了它的核心承諾：**上游重跑之後，人工校正還在。**

前面四張票各自蓋了自己那一塊的單元行為。這張票驗的是把它們串起來之後的那件事——而那件事就是整個 feature 存在的理由，必須有測試直接蓋到，不能只靠「各部分都對所以整體應該也對」。

### 端到端形狀的測試

一批修訂，套在**兩份不同的上游產出**上（模擬重跑前後，其中一份多了一頁）：

- 原本錨得住的修訂在兩份上都套上，值相同
- 新增的那頁不受任何修訂影響，拿到的是 AI 的新描述
- 沒有任何一筆有效修訂在第二份上莫名消失

這是純函式層的測試，用手寫 fixture，不碰檔案系統。

### 真實專案實跑

拿 `output/new_0724_AI六大模組管理平台_桃園智發會_最新版`（41 頁、257 個 action）跑一輪完整流程：提幾筆修訂、重跑 `f2w-describe` 與 `f2w-breakdown`、看校正是否回來。

**特別要數的一項**：後端修訂變孤兒的比例。spec 的假設是「補漏（自訂 id 的 `upsert`）比改錯（錨在 AI 生成 id 的 `set`）常見，所以後端 id 漂移的影響可控」——這個假設**沒有實測支撐**。如果孤兒比例高，`BE` 的錨定策略要重新設計，那會是一張新票，不在本票範圍內；本票只負責量出數字並記下來。

### 總說明 skill

`f2w-revise` 到這裡才算完整可用，這時把它加進總說明的管線步驟清單，標為**可選插入步**。

**總說明 skill 有 `.claude` 與 `.agents` 兩份鏡像，改一必改另一。**

## Acceptance criteria

- [ ] 端到端測試：同一批修訂套在兩份不同上游產出上（其中一份多一頁），錨得住的修訂在兩份上結果相同
- [ ] 同一測試斷言新增的那頁拿到 AI 的新描述、不受修訂影響
- [ ] 拿 `new_0724_AI六大模組管理平台_桃園智發會_最新版` 實跑：提修訂、重跑 `f2w-describe`，校正回到 `workflow.json`
- [ ] 同一專案實跑：提修訂、重跑 `f2w-breakdown`，校正回到 `workitems.json`
- [ ] 數出後端修訂變孤兒的比例並記錄在 spec 的 Further Notes（數字本身不設門檻，超標的處置是另一張票）
- [ ] 總說明 skill 加上 `f2w-revise` 這個可選插入步
- [ ] `.claude` 與 `.agents` 兩份總說明鏡像內容一致
